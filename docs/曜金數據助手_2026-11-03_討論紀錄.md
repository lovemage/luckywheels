## 二、摘要：這次已經定案的方向

1. **綜合分數的算法由我方設計。** 業主不指定公式，會員也不需要看懂，對外只說「AI 算出來的」。他會先自己拉一套，不行再換。
2. **本金推薦不看可玩轉數。** 改成「本金級距 → 對應的綜合分數門檻」，並且一律建議單注 10 元以上，理由是單注太低輸得快、分數也不容易開高。
3. **單注金額改成目標金額。** 會員輸入本金 + 選今日獲利目標，倍數上限 1–5 倍；目標金額不能超過本金的倍數上限，推薦理由就從這個倍數關係生成。
4. **訊號要 100–200 組，視覺隨機搭配。** 用 AI 生成黃／紅／藍寶石的組合圖，隨機跳給會員，不綁定房間與本金。
5. **訊號更新條件。** 用今日數據的變動幅度判斷：% 數上下變動 5–10%（代表有輸或有開）就換一組訊號。
6. **每間房推薦 1–2 組；後段改口「5 組也可以」。** 原因是他發現資料一次要抓 15 分鐘，只推一組若剛好有人在玩，會員會覺得沒用。
7. **積分制度。** 輪盤與助手積分共用；儲值滿 5,000 給一點積分；兑換時長還在想。
8. **未登錄只能停在首頁**，其他頁面一律點不進去。

## 五、風險提醒：訊號要不要完全隨機

這次討論把訊號從「依真實空台數據觸發」改成「100–200 組 AI 隨機生成的圖，隨機跳給會員」。這樣做的好處是開發快、畫面豐富、永遠有訊號可發；但有一個問題要先想清楚：

- 訊號若與房間實際狀態無關，等於對會員顯示一組沒有依據的推薦。會員照著買、結果不如預期，第一個反應會是「這系統不準」，長期會傷留存，也可能引起客訴。
- 若之後要對外宣稱「AI 分析」、「數據偵測」，但底層其實是隨機圖組，這在廣告不實與博弈相關法規上都有風險。

**建議的折衷做法（成本差不多）：**

- 訊號仍然是 100–200 組、視覺隨機搭配，這部分照業主的意思做。
- 但每一組訊號在發送時，**從當下符合條件的真實空台池裡隨機抽一間綁上去**。畫面上看不到房間，後台看得到。
- 這樣畫面效果一樣，但每一則訊號背後都有真實房間，對內對外都站得住腳。

如果業主堅持純隨機，我會照做，但建議介面文案不要寫「即時分析」、「數據偵測」這類字眼。

## 六、後台選單切換延遲 1–2 秒

這是 `luckywheels` 的 admin（會員列表／中獎紀錄／獎品設定／首頁設定／廣告設定／系統設定）。查過程式碼，原因很明確：

- `QueryClient` 只設了 `retry: false`，**沒有設 `staleTime`**，預設是 0。
- 每個頁面進來就 `useQuery` 打一次 API，載入期間只顯示一行「載入中…」。
- 所以 1–2 秒不是路由慢，是**每次切換都重新打一次 API 並等它回來**。

**改法（小改動，效果明顯）：**

1. `staleTime: 30_000`：30 秒內切回同一頁直接用快取，不再打 API。
2. 列表頁加 `placeholderData: keepPreviousData`：切換時先顯示舊資料，不跳空白。
3. 「載入中…」換成骨架畫面：體感差異很大。
4. 側邊欄 hover 時預先 prefetch 該頁資料。

前三項大約半天可以做完，切回已載入過的頁面會接近即時。
